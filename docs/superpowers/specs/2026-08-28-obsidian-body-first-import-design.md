# Obsidian 正文优先导入设计

## 背景

当前工作台只把带有 `alibaba-listing-batch` JSON 机器数据块的 Markdown 视为有效批次。Listing 正文已经包含标题、十条自定义属性、五组 FAQ 和五条卖点，机器数据块却重复保存相同内容。只生成正文的 Agent 因此无法直接使用工作台，用户还需要额外请求 Codex 补写机器数据块，这与自动上品目标冲突。

## 目标

- 工作台直接读取 Obsidian Markdown 正文，并以正文作为唯一真实内容源。
- 每份 Markdown 固定包含五套方案；用户手动发布其中一套后，在工作台选择对应方案并填写母商品 ID。
- 工作台排除母商品方案，只准备剩余四套类似品。
- 解析过程完全在本地完成，不调用 AI，不消耗模型 Token。
- 内容不完整时显示精确、可操作的错误，并继续禁止预览和草稿创建。
- 已有机器数据块文件继续可用，但机器数据块不再决定标题、卖点、属性或 FAQ。

## 非目标

- 不支持任意自由格式或由 AI 猜测字段含义的 Markdown。
- 不改变“五套方案中手动发布一套、工作台处理剩余四套”的业务流程。
- 不放宽草稿创建确认、预览指纹、卖点字段绑定和正式发布门禁。
- 不自动修改用户的 Obsidian 文件，也不自动补写机器数据块。

## 正文格式契约

工作台按下列可读结构解析正文：

1. 文件标题用于批次名称，优先读取一级标题 `<产品名称> 国际站发品方案`；无法提取时使用文件名。
2. 必须恰好存在 `## 方案 1` 至 `## 方案 5` 五个互不重复的方案区段，冒号后的流量侧重说明可选。
3. 每个方案必须包含一行非空的 `- **Title:** <英文标题>`。
4. 每个方案必须包含一个 `### 10 Custom Attributes` 区段，并能解析出恰好十条 `序号. Key: Value`；Key 不得重复，Key 和 Value 均不能为空。
5. 每个方案必须包含一个 `### 5 FAQs` 区段，并能解析出恰好五组 `Q` 和 `A`；“埋入关键词”只作为正文说明，不进入阿里 FAQ 数据。
6. 每个方案必须包含一个 `#### Selling Points` 区段，并能解析出恰好五条以 `•`、`-` 或 `*` 开头的非空卖点。发送至阿里前统一去除 Markdown 或 Obsidian 项目符号。
7. `selling-points:start/end` 注释可保留用于提高边界稳定性，但不是有效批次的必要条件；存在时必须成对出现且只包围当前方案的卖点区段。

解析器不读取关键词表格、中文翻译、首图建议、Excel 更新记录或校验摘要作为发品字段。

## 数据模型与兼容策略

新增一个正文解析入口，把 Markdown 转换为现有 `validateListingBatch` 所需的规范化对象：

- `schemaVersion` 固定为当前受支持版本。
- `batchId` 优先复用有效旧机器块中的 ID，以保持已有草稿记录兼容；没有有效机器块时，仅从规范化相对路径生成稳定摘要，正文修改不会产生一个全新的批次身份。
- `batchName` 来自一级标题或文件名。
- `plan-1` 至 `plan-5` 根据方案编号生成。
- `title`、`sellingPoints`、`customAttributes` 和 `faqs` 全部来自正文。

旧机器数据块仍可被识别，用于兼容已有文件和发现格式冲突，但不得覆盖正文内容。若正文与机器块不一致，工作台采用正文并显示“机器块内容已过期，当前按正文读取”的非阻断提示。若正文有效，即使机器块缺失、格式错误或版本过旧，文件仍可载入。

## 数据流

1. 扫描固定 Obsidian 目录内的 Markdown。
2. 对每个文件运行正文解析和严格校验。
3. 列表展示批次名称、路径及有效状态；有效性不再取决于机器块。
4. 自动选择并载入最新有效正文批次。
5. 用户选择已手动发布的母方案并填写母商品 ID。
6. 工作台只读加载母商品 Schema，排除所选方案，生成剩余四套方案。
7. 后续图片、预览、草稿确认和只读核对流程保持不变。

## 错误处理

错误必须包含文件、方案和字段位置，例如：

- `方案 3 缺少 Title`
- `方案 2 的 Custom Attributes 需要 10 条，实际 9 条`
- `方案 5 的第 4 条 FAQ 缺少 Answer`
- `方案 1 的 Selling Points 需要 5 条，实际 4 条`
- `方案编号必须恰好为 1、2、3、4、5`

无效文件仍显示在目录列表中，但禁用载入。工作台不得尝试用 AI、关键词表或相邻方案推断缺失内容。

## 生成规范同步

`generate-alibaba-listings` 的输出模板继续保持当前人类可读结构，并明确正文格式本身就是工作台输入契约。后续 Agent 不需要生成 JSON 机器数据块；只要正文通过标题、属性、FAQ 和卖点的结构校验，即可直接进入工作台。

本次仓库改造不修改真实 Obsidian 文件。对共享 Skill 的模板更新应作为独立、明确授权的后续操作，避免把仓库代码变更与全局 Skill 变更混在一次提交中。

## 安全边界

- 正文解析只读取最大 2 MiB、位于固定 Obsidian 根目录内的 `.md` 文件，并沿用路径穿越与符号链接防护。
- 正文解析成功不代表可以创建草稿；仍需母商品只读加载、图片银行就绪、卖点字段确认、完整预览通过和逐商品确认。
- 正式发布接口继续锁定。
- 机器块不得绕过正文校验或草稿门禁。

## 测试与验收

### 解析单元测试

- 无机器块但正文完整的五方案 Markdown 可成功解析。
- 有机器块但正文内容不同，以正文结果为准并返回兼容提示。
- `•`、`-` 和 `*` 三种卖点项目符号都能解析，输出均不包含项目符号。
- 缺标题、属性数量错误、FAQ 不完整、卖点数量错误、方案编号重复或缺失时返回精确错误。
- 现有带机器块的 `反光T恤4` 格式继续通过。

### 服务和界面测试

- `/api/obsidian/batches` 将正文完整的 `反光布贴.md` 标记为有效。
- 工作台启动后自动载入最新有效正文批次。
- 文件列表不再显示“缺少阿里发品机器数据块”。
- 选择一套母方案后只生成其余四套。
- 无效正文不能进入预览或草稿创建。

### 回归验收

- 运行全量 `npm test`。
- 使用 `反光布贴.md` 做本地只读验收，确认五套标题、五十条属性、二十五组 FAQ 和二十五条卖点均被识别。
- 不调用阿里草稿创建或正式发布接口完成本功能验收。

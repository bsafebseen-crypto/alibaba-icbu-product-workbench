# Obsidian 单商品一键正式发布与自动恢复设计

日期：2026-09-08

## 背景与范围

现有 Obsidian 类似品模块已经能为四个待发布方案生成完整预览，并在每张方案卡上单独创建和只读核验草稿。用户现在要求在每张方案卡的草稿按钮下增加一个正式发布按钮：单击一次即正式发布当前商品，不创建草稿、不弹确认框、不要求输入确认文字，也不连带发布另外三件。

本设计取代 `2026-08-25-obsidian-similar-product-publishing-design.md` 中“批次级一次发布四件”的交互方式。既有 Obsidian 导入、母商品读取、图片银行、Schema 可变字段边界和本地完整预览规则继续有效。

## 已批准的交互

每张待发布方案卡显示两个独立按钮：

1. `确认并创建此商品草稿`：保留现有草稿流程。
2. `直接正式发布此产品`：红色危险操作按钮，单击即授权正式发布当前方案。

正式发布按钮本身就是针对当前商品的一次明确授权，不再出现二次确认。点击后立即禁用整个工作台内所有草稿和正式发布按钮；只有当前写请求结束并进入可证明的终态后，才允许下一次商品写操作。页面关闭或刷新不会触发第二次发布。

## 采用方案

采用“单次正式写入 + 持久化状态机 + 自动只读核验与丢失响应找回”。

- `alibaba.icbu.product.schema.add` 对一个已通过完整预览的方案只调用一次。
- 工作台在调用前持久化方案指纹、请求开始时间和同标题商品基线。
- 返回商品 ID 后自动读取正式商品并核对内容。
- 请求超时或响应丢失时不盲目重发，而是通过商品列表寻找基线之后出现的候选商品，再逐个读取 Schema 并与预览指纹比对。
- 核验过程可以自动轮询和跨页面刷新恢复，但只执行只读接口。

不采用以下方案：

- 收到 `product_id` 就直接显示成功：此前已经证明返回 ID 不等于记录稳定存在。
- 超时后自动再次调用正式发布：正式发布接口没有客户端幂等参数，可能创建重复商品。
- 先创建草稿再转正式商品：不符合“不创建草稿”的目标。
- 一次点击发布四件：不符合每张卡片只发布当前一件的授权边界。

## 官方接口依据

正式发布使用 `alibaba.icbu.product.schema.add`。官方文档当前列出的发布入参为 `version`、`publish_type`、`cat_id`、`language` 和 `xml`；返回 `product_id`、`biz_success`、`message`、`msg_code` 和 `trace_id`。文档没有客户端幂等键。

自动找回使用 `alibaba.icbu.product.list`。该接口支持按 `subject`、`category_id`、`gmt_modified_from`、`gmt_modified_to`、`status`、`display` 和商品 ID 查询，并按修改时间倒序返回。候选商品详情和 Schema 继续使用现有只读 `alibaba.icbu.product.get` 与 `alibaba.icbu.product.schema.render`。

接口链接：

- [正式发布](https://open.alibaba.com/doc/api.htm#/api?cid=20966&path=alibaba.icbu.product.schema.add&methodType=GET/POST)
- [商品查询](https://open.alibaba.com/doc/api.htm#/api?cid=20966&path=alibaba.icbu.product.list&methodType=GET/POST)
- [商品详情](https://open.alibaba.com/doc/api.htm#/api?cid=20966&path=alibaba.icbu.product.get&methodType=GET/POST)
- [正式商品 Schema](https://open.alibaba.com/doc/api.htm#/api?cid=20966&path=alibaba.icbu.product.schema.render&methodType=GET/POST)

## 发布前门禁

单击正式发布按钮后，服务端必须按顺序完成以下检查，任一失败都不得调用正式发布：

1. 预览会话、任务和方案均存在，方案状态允许首次正式发布。
2. 浏览器提交的预览指纹、会话指纹和持久化任务指纹完全一致。
3. 当前卖点字段绑定仍与生成预览时一致。
4. `type.available.get` 仍确认账号、类目、语言和商品类型具备发布权限。
5. 标题、卖点、5 条 FAQ、10 条自定义属性和 6 张图片均已通过现有完整预览校验。
6. 未识别或受保护的价格、SKU、标准属性、物流和详情字段没有变化。
7. 使用 `product.list` 按当前标题、类目和时间范围读取发布前候选 ID 基线；基线读取失败时阻止发布。
8. 当前进程不存在其他阿里商品写操作。

检查通过后，先原子持久化 `publishing` 状态和基线，再调用一次 `schema.add`。不得把完整 XML、凭证或图片字节写入任务或日志。

## 全局串行与速度控制

服务端维护一个全局商品写锁，覆盖 `schema.add.draft` 和 `schema.add`，不只限制当前预览会话。锁定期间：

- 所有方案的草稿和正式发布按钮禁用；
- 第二个写请求返回明确的冲突状态，不进入阿里客户端；
- 当前写请求完成后至少等待一个短冷却周期，再开放下一件；
- 图片上传和只读查询不占用商品写锁；
- 进程意外退出时，重新启动后根据持久化状态进入只读核验，不重新执行正式发布。

首版冷却周期固定为 3 秒，不增加可配置项。它用于避免用户连续快速点击，不作为阿里限流保证。

## 状态机

正式发布使用独立状态，不能借用草稿成功状态：

`preview_ready → publishing → reconciling → published_verified`

异常终态和等待状态：

- `publish_rejected`：阿里明确返回 `biz_success=false`，可证明未成功。
- `reconciling`：请求结果不确定或商品尚未在读取接口可见，后台只读核验继续进行。
- `reconciliation_ambiguous`：找到多个无法唯一判定的候选；禁止再次正式写入，继续周期性只读核验。
- `reconciliation_unresolved`：连续核验 24 小时仍无法唯一确认；停止轮询并永久禁止该尝试再次写入，页面保留诊断信息。

每个方案最多存在一个正式发布尝试记录。任务保存状态、指纹、开始时间、核验时间、脱敏错误码、`trace_id`、候选商品 ID 和最终正式商品 ID。成功后同一方案和指纹永久禁用草稿与正式发布按钮。

## 正常成功路径

1. `schema.add` 返回 `biz_success=true` 和 `product_id`。
2. 工作台进入 `reconciling`，通过 `product.get` 确认商品存在。
3. 通过 `schema.render` 读取正式商品 Schema。
4. 使用现有比较器核对标题、卖点、FAQ、10 条属性和 6 张图片；允许阿里已知的无语义顺序规范化，但不允许值差异。
5. 核对一致后进入 `published_verified`，卡片显示 `正式发布成功 · 商品 ID`。

拿到 ID 但暂时读取不到时仍保持 `reconciling`，不能提前显示成功，也不能重新发布。

## 响应丢失后的自动找回

当写请求超时、连接断开或返回结构无法判定时：

1. 保留 `publishing` 前保存的同标题商品 ID 基线。
2. 进入 `reconciling`，调用 `product.list`，条件至少包含完整标题、类目、语言和从请求开始前少量时钟偏移到当前时间的范围。Schema 使用的 `en_US` 必须显式映射为该列表接口要求的 `ENGLISH`，不能把两个接口的语言枚举混用。
3. 丢弃基线中已经存在的 ID，只检查新候选。
4. 对每个新候选调用 `product.get` 和 `schema.render`。
5. 使用预览指纹对应的完整可变字段和图片信息进行精确比较。
6. 恰好一个候选一致时恢复其商品 ID并进入 `published_verified`。
7. 暂无候选时按退避计划继续只读轮询；多个一致候选时进入 `reconciliation_ambiguous`，继续核验但绝不再次写入。

轮询计划使用 2、5、10、20、30、60 秒，之后每 5 分钟一次，最长持续 24 小时。状态和下次核验时间持久化；工作台服务重启后恢复未完成核验。24 小时后仍不能唯一确认时进入 `reconciliation_unresolved`，保留候选和追踪号但不再写入。该后台工作只允许调用三个只读接口，不监听 Obsidian 文件、不发布其他方案。

## 可自动处理与不可猜测的错误

工作台自动处理：

- Access Token 可安全刷新时先刷新，再执行尚未开始的首次发布；
- 限流或读取接口暂时不可用时退避只读核验；
- 正式商品存在但索引尚未同步时持续轮询；
- 页面刷新、浏览器关闭和本地服务重启后的核验续跑；
- 返回 ID 丢失但能通过基线差异与 Schema 指纹唯一找回的情况。

工作台不得“自动修复”：

- 猜测或生成价格、SKU、库存、认证、物流、标准类目属性；
- 为通过校验而删除 FAQ、属性、图片或受保护字段；
- 在发布结果未知时再次调用 `schema.add`；
- 把多个候选随便选一个当成成功商品。

阿里明确拒绝时，页面显示脱敏后的具体字段错误和追踪号，状态为 `publish_rejected`。用户修正源 Listing 或母商品数据并重新生成完整预览后，新的指纹才能发起新尝试。

## 页面表现

每张方案卡新增红色 `直接正式发布此产品` 按钮。按钮只在完整预览有效、图片已就绪、卖点绑定已确认且该方案没有草稿或正式商品成功记录时启用。

点击后的文案依状态变化：

- `正在正式发布…`
- `阿里正在同步，工作台自动核验中…`
- `正式发布成功 · <商品 ID>`
- `阿里明确拒绝 · 查看原因`
- `正在自动辨认发布结果，禁止重复提交`

页面顶部显示当前全局写锁和正在处理的方案。草稿和正式发布共用同一锁，避免两类写请求并发。刷新页面后从任务记录恢复真实状态，不用浏览器内存猜测。

## 安全边界调整

实施时同步修改根目录 `AGENTS.md`，把 `schema.add` 的绝对禁止调整为以下窄授权：

- 仅 Obsidian 类似品模块可以调用；
- 仅用户单击当前方案卡的正式发布按钮后调用；
- 必须绑定当前完整预览指纹并先持久化 `publishing`；
- 必须先取得商品列表基线并持有全局商品写锁；
- 每个尝试最多调用一次 `schema.add`；
- 结果不确定时只允许自动只读找回，禁止再次写入；
- 不得调用更新、上下架、删除或库存修改接口；
- 自动测试和开发调试不得连接真实正式发布接口。

这一授权不扩展到其他模块、后台定时任务或无人触发的自动发布。

## 组件改动

- `src/alibaba-client.js`：增加正式发布和商品列表读取的严格客户端函数。
- `src/publishing-state.js`：增加正式发布状态转换和单次尝试约束。
- `src/obsidian-task-store.js`：安全持久化发布状态、基线和自动核验进度。
- `src/server.js`：增加单商品正式发布路由、全局写锁和只读核验调度。
- `public/obsidian-publishing.js`：增加每卡发布按钮、全局锁显示和状态恢复。
- `AGENTS.md`：记录经过评审的正式发布窄授权。

不引入数据库、前端框架、任务队列依赖或大模型调用。

## 测试策略

所有测试使用虚构商品 ID、mock 阿里响应和临时任务目录，绝不调用真实阿里写接口。

1. API 客户端：验证 `schema.add` 的签名、参数白名单、成功、明确拒绝、超时和脱敏响应。
2. 基线查询：验证标题、类目、语言和时间参数，以及最多 30 条候选限制。
3. 状态机：验证调用前持久化、每个尝试只写一次、成功、拒绝、核验中和歧义状态。
4. 全局串行：草稿与正式发布互斥，冷却期间第二次请求不能进入客户端。
5. 正常核验：返回 ID 后必须经 `product.get` 与 `schema.render` 完整比对才能成功。
6. 自动找回：超时后从基线之外唯一候选恢复 ID，不执行第二次 `schema.add`。
7. 歧义保护：零候选继续轮询，多候选不猜测、不重发。
8. 续跑：页面刷新和服务重启后只恢复只读核验。
9. UI：每卡两个按钮、单击无弹窗、全局锁、各状态文案和成功后永久禁用。
10. 回归：现有 Obsidian、图片银行、草稿核验、OAuth、询盘和全量测试继续通过。

## 验收标准

- 每张待发布方案卡都有独立的红色正式发布按钮。
- 单击按钮后无需输入或再次确认，只发布当前一件。
- 任一时刻最多存在一个阿里商品草稿或正式发布写请求。
- 正式发布请求对一个尝试最多发送一次。
- 返回商品 ID 后必须自动读取并核对一致才显示成功。
- 响应丢失时工作台能基于发布前基线和完整 Schema 指纹自动找回唯一商品。
- 页面刷新和服务重启不会重复发布，并能继续只读核验。
- 结果未知或候选歧义时不创建第二件商品。
- 不修改、下架、删除任何已有商品，不猜测受保护字段。
- 凭证、完整 XML、图片字节和真实任务数据不进入 Git 或日志。
- 全量自动测试通过，开发验收阶段没有真实正式发布调用。

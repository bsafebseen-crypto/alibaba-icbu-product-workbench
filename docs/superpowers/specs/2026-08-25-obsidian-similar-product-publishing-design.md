# Obsidian 类似品草稿与可信自动发布设计

日期：2026-08-25

## 目标

在现有阿里国际站本地工作台中增加独立的“Obsidian 上品”模块。Codex 或其他内容生成流程先把同一产品的 5 套 Listing 写入 Obsidian；用户任选其中 1 套手工发布为基准商品，工作台读取该线上商品的 Schema，再把其余 4 套内容与本地图片合成为 4 个类似品。

初始阶段只逐份保存 API 草稿。完整流程经过一个批次的真实草稿验收后，用户可以主动解锁“可信自动正式发布模式”：工作台上传图片并直接正式发布 4 个类似品，跳过草稿且不逐份确认。

本模块是本机 Node.js 工作台中的确定性数据流程。读取 Obsidian、修改 Schema、上传图片和调用阿里接口本身不调用大模型；现有 AI 生成功能继续作为独立可选能力，并明确产生模型服务商用量。

## 已确认的业务流程

1. Listing 生成流程在 `C:\obsidian\obsidian\国际站发品` 下写入包含 5 套方案的 Markdown。
2. 用户在工作台中手工选择一个 Markdown 批次，不自动导入最新文件。
3. 工作台解析并校验其中的版本化 JSON 数据，同时展示可读 Markdown 内容。
4. 用户任选 5 套中的一套作为基准方案，并在阿里国际站后台手工发布该方案。
5. 用户在工作台输入已发布的基准商品 ID。
6. 工作台只读获取该商品的类目和完整可编辑 Schema。
7. 被选为基准的方案不再生成；剩余 4 套按原顺序成为类似品 1 至 4。
8. 用户在工作台重新选择本地图片，分别指定 4 张主图和每套 5 张副图。
9. 工作台上传实际使用的图片到阿里图片银行，并把返回的 `file_id` 和 `photobank_url` 写入对应 Schema 图片字段。
10. 工作台只替换已确认允许变化的字段，生成 4 份完整预览。
11. 调试期逐份确认并调用 `alibaba.icbu.product.schema.add.draft` 保存草稿。
12. 可信自动模式下，用户点击一次“开始自动正式发布”，工作台对 4 套分别调用 `alibaba.icbu.product.schema.add`；不创建草稿，也不逐份确认。

工作台不会监控文件夹后自动提交。无论哪种模式，都必须由用户在当前批次页面主动启动外部写操作。

## 采用方案

采用“人类可读 Markdown + 版本化嵌入 JSON + Schema 克隆”的方案。

- Markdown 供用户在 Obsidian 中阅读和修改。
- 嵌入 JSON 是工作台唯一可信的结构化输入，避免依赖标题层级或自然语言解析。
- 线上基准商品 Schema 是价格、SKU、标准类目属性、物流、详情等不变字段的来源。
- 工作台只应用明确的字段差异，不重新构造整份商品数据。

不采用以下方案：

- 自动导入最新 Markdown：容易误选仍在生成或尚未审核的批次。
- 直接解析自由格式 Markdown：格式轻微变化就可能映射错误。
- 浏览器自动点击卖家后台表单：页面变化脆弱，且难以证明字段修改边界。
- 后台常驻监控并自动发布：缺少明确的当前批次启动动作，风险过高。

## Obsidian 数据契约

每个文件保留现有可读正文，并嵌入一个标记清晰的 JSON 代码块。首版数据结构为：

```json
{
  "schemaVersion": 1,
  "batchName": "反光T恤4",
  "sourceImageHint": "D:\\example\\source-images",
  "plans": [
    {
      "planId": "plan-1",
      "title": "...",
      "sellingPoints": "...",
      "faqItems": [
        { "question": "...", "answer": "..." }
      ],
      "customAttributes": [
        { "name": "...", "value": "..." }
      ],
      "keywords": ["..."]
    }
  ]
}
```

规则如下：

- `schemaVersion` 必须是工作台明确支持的整数版本。
- `plans` 必须正好 5 项，`planId` 必须唯一。
- 每套标题和卖点非空。
- 每套必须正好包含 5 组完整 FAQ。
- 每套必须正好包含 10 条名称和值均非空、名称不重复的自定义属性。
- `sourceImageHint` 只作界面提示，不自动读取、不自动上传，也不作为发布数据。
- 关键词供审阅和追踪，不覆盖基准商品未被本设计列入可变范围的关键词 Schema 字段。
- 旧 Markdown 没有受支持 JSON 时明确拒绝导入，不猜测解析。

## Schema 修改边界

每个类似品以线上基准商品 Schema 为模板，只允许修改以下内容：

- 商品标题；
- 主题卖点／Product Summary；
- FAQ 前 5 组；
- 商品图片：1 张主图加 5 张副图；
- 自定义属性容器：完整替换为该 Obsidian 方案中的 10 条自定义属性。

FAQ 的最终前 5 组必须与当前 Obsidian 方案完全一致；基准商品第 6 组及以后保持原值。如果真实 Schema 的 FAQ 容器无法可靠容纳 5 组，必须阻断而不是删减、拼接或覆盖后续 FAQ。

自定义属性的“完整替换”只作用于已可靠识别的自定义属性容器。不得把这 10 条写进标准类目属性容器，也不得保留基准商品旧的自定义属性。

以下内容全部继承基准商品并保持原值：

- 类目和标准类目属性；
- 品牌、认证及其他平台结构化字段；
- SKU、销售属性、价格、MOQ、库存；
- 运费模板、重量、尺寸、交期及物流属性；
- 商品详情、分组、交易和定制设置；
- 未被本设计明确列出的任何 Schema 字段。

如果标题、卖点、FAQ、自定义属性或图片中的任一字段角色无法从真实 Schema 中可靠识别，整个批次在图片上传和商品提交前停止。不得通过显示名称相似或位置相近进行猜测性写入。

## 图片流程

Obsidian 只保存图片来源提示。实际图片必须由用户在当前工作台会话中重新选择。

- 4 张主图固定对应类似品 1 至 4。
- 每套必须分配 5 张副图；副图可来自共享素材池，但同一套内不得重复。
- 工作台只上传当前 4 套实际引用的图片。
- 上传使用 `alibaba.icbu.photobank.upload`，必填 `file_name` 和 `image_bytes`，可选 `group_id`。
- 工作台保存返回的 `file_id`、`photobank_url` 和原本地文件名，不保存图片 Base64。
- Schema 图片字段同时写入图片银行 URL 和 `fileId`。
- 已成功上传且本地内容指纹一致的图片可以在当前任务中复用，避免重复上传。

本地路径或浏览器对象 URL 不得写入阿里商品 Schema。

## 提交模式

### 草稿调试模式

这是新模块的默认且初始唯一可用模式。

- 4 套内容逐份进入完整预览。
- 用户对每一套分别确认。
- 确认后调用 `alibaba.icbu.product.schema.add.draft`。
- 成功记录草稿明文 `product_id`、`request_id`、`trace_id` 和时间。
- 不调用正式发布接口。

### 可信自动正式发布模式

此模式默认锁定。只有满足以下条件后才允许用户主动解锁：

1. 一个真实批次的 4 套商品均已通过本地完整校验；
2. 4 套均已成功保存为 API 草稿；
3. 用户在阿里侧检查草稿内容，并在工作台明确标记该批次验收通过；
4. 用户在设置中明确开启“可信自动正式发布模式”，接受其会创建正式商品的说明。

解锁后，每个新批次仍先完成导入、基准绑定、图片分配和完整本地预览。用户点击一次“开始自动正式发布”即代表对当前 4 套的批次级授权；随后不再弹出逐商品确认，也不创建草稿。

自动模式只调用 `alibaba.icbu.product.schema.add` 创建新商品，不更新、下架或删除任何已有商品。它不是后台定时任务，也不会因为 Obsidian 出现新文件而自动运行。

可信模式状态保存在本机配置中，不进入 Git。关闭后立即回到草稿调试模式。重新授权阿里账号、Schema 规则版本变化或关键字段识别规则变化时自动锁回调试模式，要求重新完成验收。

## 提交前检查

任何图片或商品写操作前，工作台必须完成以下检查：

- OAuth Token 有效；
- 当前应用具备所需 API 权限；
- 使用 `alibaba.icbu.product.type.available.get` 按类目和语言查询商家发品能力；
- 基准商品类目与已渲染 Schema 一致；
- Schema 版本、`publish_type`、语言和类目 ID 均来自已读取的真实规则，不硬编码示例值；
- 5 套 Obsidian 数据及剩余 4 套映射完整；
- 每套标题、卖点、5 组 FAQ、10 条自定义属性和 6 张图片全部通过校验；
- 所有可变字段角色均已可靠识别；
- 预览内容指纹与即将提交的数据一致；
- 当前类似品没有已成功提交的商品 ID。

任一项失败时，禁止该批次进入外部写阶段。

## 状态与重复提交保护

每个类似品独立记录状态：

`待准备 → 待预览 → 待确认/待批次启动 → 上传图片中 → 提交中 → 草稿成功/正式发布成功/失败`

- 草稿调试模式使用“待确认”；可信自动模式使用“待批次启动”。
- 成功提交后保存返回的商品 ID，并禁用同一内容指纹的再次提交。
- 提交中的请求不得由重复点击再次发起。
- 单套业务失败不回滚其他已经成功的商品，也不自动重试；自动模式继续处理剩余套数并在批次结束后汇总失败项。
- 如果本地任务记录缺失或内容指纹发生变化，必须重新预览，不能沿用旧成功状态。
- 阿里接口没有客户端幂等键时，本地保护不能替代服务端幂等；超时且无法确定结果时标记为“结果未知”，禁止重试，先用只读商品查询核实。

## 页面结构

左侧导航新增独立的“Obsidian 上品”，不扩展现有长表单。页面采用已确认的五步引导布局：

1. 导入方案：浏览固定 Obsidian 根目录并手工选择 Markdown。
2. 绑定基准：选择 5 套中的基准方案，输入线上基准商品 ID，读取 Schema。
3. 分配图片：选择本地图片，固定 4 张主图并分配每套 5 张副图。
4. 完整预览：按类似品展示原值、新值、图片和保持不变字段摘要。
5. 提交方式：调试模式逐份保存 API 草稿；可信模式一次启动整批正式发布。

页面始终明显显示当前模式。可信自动模式使用明确的危险级视觉标识，但不使用重复弹窗干扰已经授权的批次执行。

## 本地存储与敏感信息

本地任务可以保存：

- Obsidian 文件路径、内容哈希和 `schemaVersion`；
- 基准方案 ID、基准商品 ID和类目 ID；
- 4 套规范化内容、图片文件名与分配关系；
- 图片银行 `file_id` 和 URL；
- Schema 字段角色、变更摘要和内容指纹；
- 草稿或正式商品 ID、请求 ID、追踪 ID、状态和时间。

不得写入任务、日志、Obsidian 或 Git：

- App Secret、Access Token、Refresh Token、AI API Key；
- 图片 Base64 或图片字节；
- 完整原始 Schema XML；
- 包含凭证的请求头或签名原文。

完整 Schema 只在生成预览和提交所需的当前内存中存在。日志记录接口名、脱敏参数摘要、业务状态和追踪 ID。

## API 边界

本设计依据 Alibaba.com 开放平台当前 ICBU 商品目录中的以下接口：

- `alibaba.icbu.product.schema.get`：读取新发规则；
- `alibaba.icbu.product.schema.render`：读取基准商品可编辑 Schema；
- `alibaba.icbu.product.type.available.get`：只读查询商家发品能力；
- `alibaba.icbu.photobank.upload`：上传图片银行；
- `alibaba.icbu.product.schema.add.draft`：保存商品草稿；
- `alibaba.icbu.product.schema.render.draft`：读取草稿复核；
- `alibaba.icbu.product.schema.add`：正式创建商品。

接口存在性、参数和返回值以 [Alibaba.com 开放平台 ICBU 商品 API 目录](https://open.alibaba.com/doc/api.htm#/api?cid=20966&path=alibaba.icbu.product.schema.add.draft&methodType=GET/POST) 为准，不再以淘宝开放平台旧文档页作为当前能力依据。实现前应再次核对目录、应用权限和真实 Schema 规则，但核对过程不得发送商品写请求。

旧接口 `alibaba.icbu.product.add.draft` 不用于新实现。`schema.update`、库存更新、上下架、删除及任何已有商品写操作均不在本设计范围内。

当前仓库 `AGENTS.md` 仍限制商品写接口，并把自定义属性变化限制为最多 5 项。实现开始前必须根据本设计和用户批准，单独更新项目安全边界：仅允许本模块在上述模式门禁下调用 `schema.add.draft` 或 `schema.add`，并仅允许 Obsidian 导入路径完整替换恰好 10 条自定义属性。其他现有流程继续遵守原限制。

## 错误处理

- Obsidian 文件不可读、JSON 缺失或版本不支持：拒绝导入并显示具体原因。
- 方案数量、FAQ 或属性数量不符：逐项列出错误，不创建半成品任务。
- 基准方案与线上商品内容不一致：允许继续读取线上 Schema，但必须明确显示差异供用户判断；不自动修改基准商品。
- OAuth 或权限不足：保留本地进度，仅禁用阿里步骤。
- 图片上传部分失败：成功项保留，失败项可在用户再次启动当前步骤时重试；商品提交保持禁用。
- Schema 角色无法识别或阿里规则发生变化：锁回调试模式并要求重新预览。
- 草稿或正式提交业务失败：记录 `msg_code`、`message`、`trace_id`，不自动重试。
- 请求超时且结果不确定：标记“结果未知”，通过只读查询核实后再决定，不直接重发。
- 自动模式部分成功：汇总每套商品 ID 与失败原因，不尝试删除或回滚成功商品。

## 测试策略

采用测试驱动开发，并确保自动化测试不触发真实阿里商品写接口。

1. Obsidian 解析测试：版本、五套数量、唯一 ID、标题、卖点、五组 FAQ 和十条属性校验。
2. 基准映射测试：任选五套中的一套后，准确排除基准并稳定生成其余四套。
3. Schema 修改测试：只改允许字段；完整替换十条自定义属性；标准属性、SKU、价格、详情和物流保持字节级等价。
4. 字段识别测试：未知或歧义角色必须阻断，不猜测写入。
5. 图片测试：四张主图映射稳定、每套五张副图、同套不重复、上传响应正确写入 URL 与 `fileId`。
6. API 客户端测试：用 mock 覆盖 `type.available.get`、图片上传、草稿、草稿读取和正式发布的成功、业务失败、超时及脱敏日志。
7. 模式门禁测试：默认不能正式发布；未完成草稿验收不能解锁；可信模式失效条件会自动回锁。
8. 重复提交测试：进行中、成功和结果未知状态均阻止重发。
9. 服务端路由测试：请求参数严格校验，响应不泄露凭证、图片 Base64 或完整 Schema。
10. 页面测试：五步导航、模式标识、逐份草稿确认、批次级自动启动和结果汇总。
11. 回归测试：现有 OAuth、AI、只读 Schema、图片银行、本地任务和产品池测试全部继续通过。

## 分阶段交付与验收

### 阶段一：Obsidian 离线数据链路

- 能浏览固定根目录并手工选择文件；
- 能解析版本化 JSON 并严格校验五套方案；
- 能选择任一基准并得到稳定的四套映射；
- 不调用阿里接口。

### 阶段二：完整本地准备

- 能只读加载基准 Schema；
- 能选择和分配图片；
- 能生成仅包含允许变更的四套完整预览；
- 图片上传必须由用户启动并明确确认；
- 不调用草稿或正式发布接口。

### 阶段三：真实 API 草稿

- 先完成 mock 测试和只读发品能力检查；
- 用户逐份确认并保存四套 API 草稿；
- 通过 `schema.render.draft` 复核保存结果；
- 阿里侧检查与本地预览一致后，用户标记批次验收通过；
- 不调用正式发布接口。

### 阶段四：可信自动正式发布

- 只有验收通过后才允许解锁；
- 用户对当前批次点击一次启动；
- 工作台上传所需图片并直接调用 `schema.add` 发布四套；
- 不创建草稿、不逐份确认、不后台自动运行；
- 记录每套正式商品 ID 和完整结果摘要。

每个阶段在进入下一阶段前都必须通过全量 `npm test` 和对应的人工验收。阶段三和阶段四是不同的外部写权限升级，实施时不得合并跳过。

## 非目标

- 自动生成 Obsidian Listing；
- 监听 Obsidian 文件并无人值守发布；
- 修改或删除基准商品；
- 更新、下架、删除任何已有商品；
- 自动修复价格、SKU、库存、认证或物流；
- 批量重试结果未知的请求；
- 数据库、多用户、云端同步或远程部署；
- 任何未经本设计列明的阿里写接口。

## 最终验收标准

- 用户可以从 Obsidian 手工选取一个含 5 套方案的批次，并任选其中一套绑定已发布基准商品。
- 工作台稳定生成其余 4 套，只替换标题、卖点、FAQ 前 5 组、恰好 10 条自定义属性和 6 张图片。
- 所有图片来自图片银行返回的 URL 与 `fileId`。
- 调试模式可逐份保存并读取 API 草稿，绝不正式发布。
- 未完成一个四草稿批次验收时，正式发布模式不可用。

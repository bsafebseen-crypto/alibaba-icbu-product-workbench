# 主产品 Schema 克隆与四份草稿预览设计

## 目标

用户输入一个国际站线上主产品数字 ID 后，工作台通过只读接口 `alibaba.icbu.product.schema.render` 获取原商品完整 Schema，识别标题、主题卖点和 FAQ，并生成四份可编辑的本地草稿预览。价格、SKU、主图、属性、详情、分组、物流等未知或不需要修改的字段必须原样继承。

本阶段不调用 `alibaba.icbu.product.schema.add.draft`，也不调用正式发布接口。

## 已确认前提

- 用户希望沿用一个已发布主产品，生成四个类似品。
- 四个类似品主要变化为标题、主题卖点和 FAQ。
- 原产品的图片、属性、价格、SKU 和详情不应被工作台重新生成或覆盖。
- 关键词表和 AI 生成仍可用于产生四套文案，但 AI 不直接接触阿里凭证。
- 工作台继续只监听 `127.0.0.1`。

## 方案比较

### 方案 A：结构化解析并最小修改，推荐

把 Schema XML 解析成结构化节点，建立“字段角色映射”，同时保留原始 XML。生成预览时复制原始结构，只修改已明确识别的标题、主题卖点和 FAQ 节点。

优点：边界清晰、可测试、不会因为字段顺序变化而失效，后续可直接接草稿接口。缺点：需要新增一个小型 XML 解析依赖，并用真实商品 Schema 校准字段别名。

### 方案 B：正则表达式替换 XML

直接在 XML 字符串中搜索字段 ID 和 value 属性。

优点：代码少。缺点：XML 转义、嵌套标签、多行内容和字段重复时容易误替换，存在破坏原商品其他字段的风险，不采用。

### 方案 C：使用旧版 `product.get` JSON 重建商品

读取商品 JSON 后重新拼装发布入参。

优点：业务字段看起来直观。缺点：需要手工覆盖大量类目差异字段，容易遗漏 Schema 专属规则，也无法保证与 `schema.add.draft` 的 XML 入参一致，不采用。

## 架构

新增一个独立的 `schema-template` 模块，职责限定为：

1. 解析阿里返回的 Schema XML。
2. 枚举字段 ID、名称、控件类型和当前值。
3. 根据稳定字段 ID、名称别名和节点结构识别三个可编辑角色：
   - `title`
   - `productSummary`
   - `faq`
4. 返回识别报告，不确定的字段不自动修改。
5. 接收一份文案变体，在原始 Schema 副本上更新三个已确认角色。
6. 重新序列化为可供未来 `schema.add.draft` 使用的 XML。

阿里 API 客户端只负责读取 Schema；解析与修改逻辑不放进 API 客户端，避免把网络、签名和商品结构耦合在一起。

## 数据结构

读取主产品后，服务端返回：

```json
{
  "sourceProductId": "1601915922577",
  "traceId": "...",
  "template": {
    "schemaXml": "<itemSchema>...</itemSchema>",
    "recognized": {
      "title": { "fieldId": "...", "value": "..." },
      "productSummary": { "fieldId": "...", "value": "..." },
      "faq": { "fieldId": "...", "items": [] }
    },
    "warnings": []
  }
}
```

四份本地预览每项包含：

```json
{
  "index": 1,
  "sourceProductId": "1601915922577",
  "title": "...",
  "sellingPoints": "...",
  "faq": "...",
  "previewXml": "<itemSchema>...</itemSchema>",
  "changedFields": ["title", "productSummary", "faq"],
  "status": "preview"
}
```

`previewXml` 只保存在本地任务文件中，不显示完整内容，也不发送给大模型。

## 数据流

1. 浏览器把主产品 ID 和阿里配置发送到本地服务。
2. 本地服务调用只读 `schema.render`。
3. `schema-template` 解析 XML 并返回识别报告。
4. 如果标题、主题卖点或 FAQ 无法可靠识别，页面显示具体警告；未识别字段禁止自动替换。
5. 工作台创建四个类似品编辑位，并用原商品内容作为初始值。
6. 用户手工修改或调用 AI 生成四套文案。
7. 本地服务为每套文案生成一份 `previewXml`，并返回变更摘要。
8. 用户可以逐份检查“继承字段数量、修改字段、警告”，然后保存为本地任务。

## 页面设计

主产品读取成功后，现有顶部继承提示扩展为三部分：

- 主产品 ID 与只读状态。
- 字段识别结果：标题、主题卖点、FAQ 分别显示“已识别”或“需确认”。
- 继承范围摘要：图片、属性、价格、SKU、详情等显示“保持原值”。

每个类似品编辑页继续只展示标题、主题卖点、FAQ 和关键词。底部增加“生成预览”按钮；生成后显示一个紧凑的变更摘要，不展示大段 XML。

不增加“保存到阿里”或“正式发布”按钮。

## 错误处理与安全边界

- Schema 不是有效 XML：停止生成预览，显示 Trace ID 和中文错误。
- 三个目标字段中有字段无法识别：保留原值并显示警告，不做猜测性替换。
- 标题超过 128 字符：拒绝生成该份预览。
- FAQ 格式不完整：提示用户修正，不生成该份预览。
- 解析和预览过程不记录 App Secret、Access Token 或完整授权响应。
- 任何生成失败都不覆盖当前编辑内容和原始 Schema。

## 测试策略

采用测试驱动开发：

1. 使用脱敏 Schema fixture 验证字段枚举和三个角色识别。
2. 验证只修改三个目标字段，价格、SKU、图片和任意未知节点序列化后语义保持不变。
3. 验证 XML 转义字符、多个 FAQ、空 FAQ 和无法识别字段。
4. 验证四份预览互不共享可变状态。
5. 验证 HTTP 接口不返回或记录阿里密钥。
6. 静态页面测试覆盖识别状态和“生成预览”入口。
7. 浏览器冒烟测试覆盖读取结果展示和四个版本切换。

## 验收标准

- 输入有效主产品 ID 后，可看到标题、主题卖点和 FAQ 的识别状态。
- 读取成功时四个类似品使用原商品对应文案作为初始内容。
- 修改四份文案后可生成四份本地预览 XML。
- 自动化测试证明目标字段之外的继承数据未被修改。
- 页面和服务端都不存在阿里草稿保存或正式发布动作。
- 无真实店铺数据时可使用脱敏 fixture 完成全部自动化测试；真实字段别名通过一次只读主产品加载校准。

## 后续阶段

本设计完成并通过真实只读 Schema 校准后，下一阶段才增加 `schema.add.draft`。届时仍应先逐份确认，再由用户明确触发保存草稿；正式发布继续保持独立阶段。

# Obsidian 图片银行恢复与安全续跑设计

日期：2026-08-26

## 背景

Obsidian 上品模块已经能读取五套 Listing、绑定一个已手工发布的母商品、上传图片、生成四份完整预览，并逐商品创建和读取 API 草稿。当前已创建并核对 `plan-2` 草稿；剩余方案尚未创建。

为了避免泄露商品数据，工作台只在内存中保留完整 Schema XML 和预览 XML。服务重启后旧预览会话按设计失效，但当前实现也会丢失本地图片与阿里图片银行 `fileId`、URL 的对应关系。因此用户即使重新选择完全相同的图片，也只能再次上传，既会产生重复图片，也无法安全恢复剩余方案的预览。

## 目标

为 Obsidian 上品模块增加可验证、可恢复的图片映射，使工作台重启后可以：

1. 由用户重新选择本地图片；
2. 根据图片内容指纹恢复已经上传的图片银行记录；
3. 只把确实没有记录的图片列为待上传项；
4. 重新读取母商品 Schema 并生成新的完整预览；
5. 跳过已经创建草稿的方案，对剩余方案继续执行现有逐商品确认流程。

本功能不保存图片内容、凭证或完整 Schema，也不调用正式发布接口。

## 采用方案

采用“本地内容指纹缓存优先，图片银行只读查询辅助恢复”的组合方案。

- 浏览器读取用户主动选择的图片并计算 SHA-256；文件名、大小和修改时间只用于界面提示，不作为唯一身份。
- 服务端保存 `SHA-256 → fileId + photobankUrl` 的脱敏映射，供同一台机器后续会话恢复。
- 对本机已有可信缓存的图片直接恢复映射，不调用阿里接口。
- 对缓存缺失的图片，允许用户启动只读的 `alibaba.icbu.photobank.list` 查询，并只在返回结果能够可靠对应当前文件时恢复。
- 无法可靠匹配的图片保持“待上传”状态；现有上传按钮列出数量并再次确认后，才调用 `alibaba.icbu.photobank.upload`。
- 每次恢复或上传后都重新生成预览指纹。旧会话 ID、旧预览指纹和旧提交授权不能复用。

不采用以下方案：

- 重启后全部重新上传：实现简单，但会制造重复图片并浪费图片银行空间。
- 只按文件名匹配图片银行记录：同名文件可能内容不同，无法证明映射正确。
- 持久化完整预览 XML：扩大敏感商品数据落盘范围，且会让已经变化的母商品 Schema 被旧预览静默复用。
- 自动扫描本地目录：当前安全边界要求图片必须由用户在工作台中主动选择。

## 数据模型

新增本机运行时图片映射存储，放在 Git 忽略的数据目录中。每条记录只包含：

```json
{
  "sha256": "64 位小写十六进制摘要",
  "fileName": "1.jpg",
  "size": 65981,
  "mimeType": "image/jpeg",
  "fileId": "阿里图片银行文件 ID",
  "photobankUrl": "https://...",
  "source": "upload 或 photobank-list",
  "verifiedAt": "ISO 时间"
}
```

约束如下：

- `sha256` 是本地文件内容的身份键。
- `fileName`、`size` 和 `mimeType` 用于审计与显示，不替代内容指纹。
- `fileId` 和 `photobankUrl` 必须同时存在，否则记录无效。
- 不保存本地绝对路径，避免目录信息泄露或换机后产生错误依赖。
- 不保存图片 Base64、字节、App Secret、Access Token、Refresh Token、请求签名、Schema XML 或预览 XML。
- 缓存写入采用临时文件加原子替换，避免进程中断留下半条记录。
- 冲突记录不自动覆盖：同一 SHA-256 对应不同有效 `fileId` 时保留原记录并要求用户重新上传或人工判断。

## 图片银行只读恢复

Alibaba.com 官方 ICBU 图片接入说明指出，已在图片银行中的图片可以通过 `alibaba.icbu.photobank.list` 获取发布所需的图片 URL 和 ID。该接口在本模块中只用于恢复候选记录，不修改图片银行或商品。

恢复流程：

1. 用户在四个方案卡中重新选择每套 6 张图片。
2. 浏览器为所有唯一文件计算 SHA-256，并把摘要、文件名、大小和 MIME 类型发送给本机服务；不在恢复请求中发送图片 Base64。
3. 服务端先查询本机缓存，返回已验证映射。
4. 对缓存缺失项，页面显示将要调用的只读图片银行查询及缺失数量。
5. 用户主动确认查询后，服务端调用 `alibaba.icbu.photobank.list`。
6. 只有响应包含完整 `fileId`、URL，且平台返回的可验证元数据足以唯一对应当前文件时，才写入恢复缓存。
7. 如果官方响应没有内容摘要或其他足以证明内容一致的字段，则不得仅凭同名自动绑定。该图片保持待上传，或者由用户在明确预览候选后单独确认绑定。

实现前先用 mock 固定客户端契约；连接真实账号后的首次只读调用只记录字段名称、数量和追踪号，不输出原始响应、凭证或无关图片 URL。若真实响应字段不足以进行可靠匹配，首版仍可交付“本地缓存恢复 + 缺失项确认上传”，而不降低匹配标准。

## 上传后的缓存写入

现有图片上传流程保持逐批明确确认。成功上传一张图片后：

1. 校验返回的 `fileId` 和 `photobankUrl`；
2. 使用上传前已经计算的 SHA-256 写入本机缓存；
3. 更新当前会话中的图片映射；
4. 单张失败时停止后续上传，并保留此前成功写入的记录；
5. 用户再次启动时先从缓存恢复成功项，只提交仍缺失的图片。

上传接口超时且结果不明确时，不把该图片写入成功缓存，也不自动重试。用户可以先启动图片银行只读查询核实，仍无法确认时再决定是否重新上传。

## 续跑状态

重启后的续跑不恢复旧内存预览，而是重建可信链路：

`重新选择文件 → 内容指纹校验 → 恢复/补齐图片映射 → 重新读取母商品 Schema → 重新生成完整预览 → 逐商品确认草稿`

已持久化的草稿结果继续作为历史事实展示：

- `draft_created` 且存在草稿 ID 的方案显示为“已创建”，不生成新的草稿按钮。
- 已创建方案可继续使用现有 `schema.render.draft` 只读核对。
- `preview_ready` 但旧预览会话已失效的方案显示为“需要重新生成预览”，不能提交旧指纹。
- `submitting` 或 `result_unknown` 继续阻止重试，必须先只读核实。
- 新预览任务应关联同一批次、母方案和母商品；界面汇总历史已完成项与本次剩余项，不把旧预览任务伪装成可续提交会话。

本批次当前应跳过已经创建并核对的 `plan-2`，剩余 `plan-3`、`plan-4`、`plan-5` 在新预览生成后仍分别点击、分别确认、分别调用草稿接口。

## 页面交互

Obsidian 上品页面的图片步骤增加三个清晰状态：

- `已从本机缓存恢复`：内容指纹匹配，显示恢复数量。
- `可查询图片银行`：本机缓存缺失，按钮明确标注这是只读查询。
- `待确认上传`：无法可靠恢复，显示真正需要上传的图片数量。

页面不要求用户手工输入 `fileId` 或 URL。重新选择图片后自动计算本地指纹，但不会因此自动访问阿里接口。任何只读查询或上传都由用户在当前页面主动启动。

预览区域同时显示：

- 历史已创建草稿的方案与草稿 ID；
- 本次需要重新预览的剩余方案；
- 每套 6 张图片是否都具有完整 `fileId` 和 URL；
- 新生成的预览指纹；
- 正式发布仍禁用。

## API 与路由边界

服务端新增的最小能力为：

- 本机图片缓存查询：输入多个 SHA-256，返回命中的安全映射；
- 图片银行只读列表代理：严格校验分页和筛选参数，返回规范化的候选元数据；
- 上传成功缓存写入：仅由现有上传路由在收到有效阿里响应后内部调用。

客户端实现 `alibaba.icbu.photobank.list` 时复用现有 TOP 签名与错误规范化逻辑。不得在 URL、响应、日志或本机缓存中暴露凭证。列表接口必须设置有限页大小和有限最大页数，禁止无界扫描整个图片银行。

现有外部写边界不变：

- `alibaba.icbu.photobank.upload`：只有用户确认待上传清单后允许调用；
- `alibaba.icbu.product.schema.add.draft`：只有当前完整预览指纹匹配且用户逐商品确认后允许调用；
- `alibaba.icbu.product.schema.add`：继续禁止，不能新增按钮、隐藏路由或自动调用；
- 不接入商品修改、上下架、删除或图片删除接口。

## 错误与冲突处理

- 文件读取或 SHA-256 计算失败：该文件保持未就绪，不调用阿里接口。
- 文件内容变化：产生新 SHA-256，旧缓存不能命中，旧预览立即失效。
- 缓存文件损坏：忽略损坏记录并显示可恢复错误，不删除用户图片或阿里图片。
- 缓存中 `fileId` 或 URL 不完整：视为未命中。
- 图片银行列表超时：保持本地进度，不自动重试。
- 候选同名但无法证明内容相同：不得自动绑定。
- 同一内容指纹出现多个冲突映射：阻断自动选择，要求重新上传或人工确认。
- 图片已经从阿里图片银行删除：在生成预览前的完整性检查中判为不可用并要求补传。
- 母商品 Schema 或规则变化：必须用最新只读结果重新生成预览，不能沿用缓存的预览指纹。

## 测试策略

采用测试驱动开发，自动化测试不连接真实阿里账号。

1. 浏览器指纹测试：相同字节得到相同 SHA-256；同名不同内容不得复用。
2. 缓存测试：有效记录命中、无效记录忽略、原子写入、冲突阻断、敏感字段不落盘。
3. 图片银行客户端测试：请求签名、分页上限、响应规范化、业务错误与超时。
4. 服务端路由测试：严格输入校验、仅返回必要字段、不泄露凭证或原始响应。
5. 上传续跑测试：部分成功后缓存，下一次只上传缺失项。
6. 页面状态测试：缓存恢复、只读查询、待上传数量和预览失效提示。
7. 草稿续跑测试：跳过 `draft_created`，拒绝旧 `preview_ready` 会话，继续逐份确认剩余方案。
8. 回归测试：草稿读取核对、属性顺序语义比较、正式发布禁用及现有全量测试继续通过。

真实账号验收分开执行：先确认只读列表的实际响应契约，再确认缓存命中；只有确实缺失的图片才进入用户确认上传。测试与验收过程中不调用正式发布接口。

## 分阶段交付

### 阶段一：本机内容指纹缓存

- 为用户选择的图片计算 SHA-256；
- 上传成功后持久化安全映射；
- 重启并重新选择相同文件后能够恢复；
- 无任何阿里调用即可完成缓存命中。

### 阶段二：图片银行只读辅助恢复

- 接入并 mock 测试 `photobank.list`；
- 用户主动启动首次真实只读查询；
- 根据真实响应字段确认可自动匹配的严格条件；
- 不满足条件的候选绝不自动绑定。

### 阶段三：Obsidian 剩余方案续跑

- 重新读取母商品并生成新预览；
- 已完成方案保持只读历史状态；
- 剩余方案逐一创建并读取核对草稿；
- 每个草稿写操作继续单独等待用户确认。

## 非目标

- 持久化或恢复旧预览 XML；
- 根据文件名猜测图片内容；
- 自动扫描本地图片目录；
- 后台轮询或无人值守调用阿里接口；
- 自动重试结果未知的上传或草稿请求；
- 创建、修改、删除或移动图片银行图片；
- 调用 `alibaba.icbu.product.schema.add` 正式发布；
- 修改、下架或删除任何现有商品。

## 验收标准

- 相同本地图片在成功上传并重启工作台后，通过 SHA-256 恢复同一 `fileId` 和 URL，不重复上传。
- 同名但内容不同的图片不会命中旧缓存。
- 本机缓存缺失时，工作台不会自动访问阿里；只读查询和上传都有明确的当前页面启动动作。
- 只读图片银行响应无法证明内容一致时，不会错误绑定候选。
- 缓存和任务文件不包含图片字节、Base64、凭证、完整 Schema 或预览 XML。
- 服务重启后旧预览权限保持失效，必须基于最新母商品 Schema 重新生成指纹。
- 已创建草稿不会重复提交；剩余方案仍遵守逐商品确认与 `submitting/result_unknown` 门禁。
- 正式发布接口在代码和界面中继续不可用。
- 全量 `npm test` 通过。

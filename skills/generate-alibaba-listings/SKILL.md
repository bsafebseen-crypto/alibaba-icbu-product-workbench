# 国际站图片选词发品

## 核心原则

把一套图片识别为一个产品。以图片相关性为硬门槛，从全部词表动态组词；用脚本校验硬规则，并且只在最终 Markdown 成功写入后更新本次来源 Excel。

## 必读资源

开始工作后完整读取：

- `references/seo-rules.md`：选词、标题、属性、FAQ、覆盖和 Excel 回写规则。
- `references/output-template.md`：最终 Markdown 的固定结构。

执行脚本，不把脚本当作提示词复述：

- `scripts/listing-tools.mjs`：校验标题、分析加权词根压缩、判定覆盖、检查型号和写入 Markdown。
- `scripts/workbook-tools.mjs`：扫描词表、生成更新计划和安全回写 Excel。

## 工作流

复制以下进度清单并依次完成：

```text
- [ ] 确认产品图片范围和方案数量
- [ ] 查看整套图片并建立产品画像
- [ ] 扫描全部 Excel 并保留关键词来源
- [ ] 过滤无关词并动态组合候选标题
- [ ] 校验并修正全部标题
- [ ] 生成唯一型号、属性、FAQ、翻译和首图建议
- [ ] 写入并验证 Obsidian Markdown
- [ ] 生成严格覆盖更新计划
- [ ] 获得写入授权后更新并复核来源 Excel
```

### 1. 检查输入

要求用户提供一个图片文件夹或明确的一组图片，以及方案数量。把全部图片当作同一产品的不同角度。缺少方案数量时只询问这一项。

### 2. 识别产品

逐张查看图片，综合提取产品类型、结构、可见材质、颜色、功能、适用人群和场景。区分“图片可确认”和“品类合理推断”。没有证据时不生成认证编号、检测标准或防护等级。

### 3. 准备 Excel 运行环境

使用 `spreadsheets:Spreadsheets` 并调用工作区依赖加载器取得 Node.js 和 `node_modules` 路径。在本次任务的可写 `work/` 目录中：

1. 建立指向加载器所给 `node_modules` 的 Junction。
2. 把本 Skill 的两个 `.mjs` 脚本复制到该 `work/` 目录。
3. 从该目录运行脚本，确保 `@oai/artifact-tool` 从官方运行时解析。

不得安装或改用 `openpyxl`、`xlsxwriter` 等其他工作簿库。

### 4. 扫描并选词

运行：

```text
node workbook-tools.mjs scan --input-dir <词表目录> --output <candidates.json>
```

扫描全部工作簿，而不是只按文件名选一个词表。对候选词执行以下顺序：

1. 排除与图片产品冲突的词。
2. 全局比较搜索指数；用高指数相关词建立流量主干，点击率用于同层比较和机会判断。
3. 必争词和精准词优先占据中心词或前置属性位置；红海词、蓝海词和未标注词补充新词根。
4. 从组标题开始就把所有符合产品且标题状态为“否”的词纳入增量覆盖池，不论搜索指数高低。含有高指数核心词根的词可直接参与主干设计；低指数“否”词也必须主动寻找共享词根或分配尚未出现的新词根，并在不同方案间轮换覆盖。不得把“否”状态词推迟到标题不足 120 字符时才补，也不得仅因指数低而跳过；每条标题同时保留必要的高指数流量基本盘。
5. 不按语言过滤；相关的小语种词与英文词一起参与指数比较和字符占位。
6. 为不同方案分配不同的高指数和低指数“否”状态增量词，扩大整批方案的未覆盖词覆盖面；允许重复必要的核心流量词。
7. 为每个入选词保留本次来源 Excel、工作表和行号。

最终 Obsidian 中必须逐条列出每套方案实际选用的全部词表关键词，不得只展示代表词。每条记录包含关键词、搜索指数、点击率、原覆盖状态、人工分类、来源 Excel、工作表和行号，并标明属于标题严格覆盖或本次选用词根覆盖。

标题采用“搜索指数加权的词根压缩”：每条标题保留高指数主干，同时从本批尚未覆盖的相关“否”状态词中持续选择高指数和低指数关键词，把它们拆成尚未出现的有效词根并跨方案分配。相同词根优先复用；允许隔山打牛、自然调序、单复数归一和小语种引流。不得套用固定词组或把完整关键词逐条拼接。

### 5. 生成并校验标题

先生成候选标题 JSON，再运行：

```text
node listing-tools.mjs validate --input <titles.json> --output <validation.json>
node listing-tools.mjs analyze --input <titles-with-keywords.json> --output <compression.json>
```

`titles-with-keywords.json` 的每项包含 `title` 和本方案实际选用的 `keywords` 记录；小语种介词或连词通过 `additionalFunctionWords` 传给校验器。逐条读取硬规则错误和压缩指标，直到标题全部通过，并确认高指数词根已覆盖、本次选用关键词的全部必要词根已进入标题、未选词有明确原因、可避免重复词根已被新流量词根替换。不得人工估算字符数或跳过脚本校验。

### 6. 完成方案内容

按 `references/output-template.md` 生成用户要求数量的方案。扫描 Obsidian 历史 Markdown，确保完整型号全局唯一；同一批方案的型号核心关键词彼此不同。

属性和 FAQ 使用英文。分析、翻译、Excel 更新记录和首图建议使用中文。属性或 FAQ 中出现的关键词不计入标题覆盖。

不同方案不得只对同一批关键词换序。除允许重复的核心流量词外，各方案的主要增量关键词、人群、场景或采购意图必须形成明显不同的关键词组。

### 7. 写入 Markdown

先通过 `output-path` 获取不覆盖旧文件的路径，再使用 `write-markdown` 原子写入。目录格式为 `国际站发品/YYYY-MM-DD/`；同名产品自动使用 `-2`、`-3` 后缀。

重新读取最终 Markdown，确认方案数量、每套十个属性、五组 FAQ、型号和标题校验结果齐全。

### 8. 计划并更新 Excel

仅在 Markdown 写入和验证成功后生成更新计划：

```text
node workbook-tools.mjs plan --titles <titles.json> --selected <selected.json> --candidates <candidates.json> --output <updates.json>
node workbook-tools.mjs apply --plan <updates.json> --temp-dir <同卷临时目录> --dry-run
```

先检查 dry-run。只有用户要求真正生成发品方案并已明确允许回写时，才把计划中的 `approvedForWrite` 设为 `true`，然后显式运行不带 `--dry-run` 的 `apply`。

开发、评估、演示和只读试运行永远不得进入写入模式。

### 9. 最终复核

报告：

- Obsidian Markdown 完整路径；
- 生成方案数量；
- 每条标题的脚本校验结果；
- 实际更新的 Excel、工作表、单元格和关键词；
- 未更新或失败的文件及原因。

不能验证 Excel 更新成功时，明确说明“Markdown 已生成，但词表未更新”，不得宣称全部完成。

## 常见错误

| 错误 | 正确做法 |
|---|---|
| 根据词表文件名只选一个词表 | 扫描全部词表，再按图片相关性过滤 |
| 把示例组合当固定模板 | 每次根据实际词库动态组词 |
| 把完整关键词逐条拼接 | 拆成词根，用一个词根承接多组关键词 |
| 为填满字符重复产品中心词 | 从剩余相关关键词和小语种词中加入尚未覆盖的新词根 |
| 只看英文词 | 所有相关语言按搜索指数、点击率和分类共同参与选词 |
| 把“否”状态词留到不足 120 字符时再补 | 从组标题开始就让相关未覆盖词参与主干和嵌套设计 |
| 只覆盖高指数“否”词 | 低指数“否”词也是增量目标，利用共享词根和多方案轮换主动覆盖 |
| 只回写连续完整短语 | 本次实际选用且全部必要词根已被标题承接的来源词也回写；未选词仍须连续严格覆盖 |
| FAQ 或属性出现关键词就更新状态 | “标题”列只认英文标题 |
| 相同关键词跨 Excel 全部更新 | 只更新本次实际选用来源文件 |
| Markdown 尚未落盘就更新 Excel | 先写入并验证 Markdown，最后回写 |
| 测试时修改真实词表 | 使用 dry-run 和临时工作簿 |
